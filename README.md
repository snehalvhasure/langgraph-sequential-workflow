# Poem Generator and Summarizer using LangGraph

A simple **LangGraph and LangChain project** that uses an OpenAI LLM to generate a 10-line poem based on a user-provided topic and then generates a summary of the poem.

## Workflow

```text
User Topic
    ↓
Generate Poem
    ↓
Generate Summary
    ↓
Final Result
```

## Technologies Used

* Python
* LangChain
* LangGraph
* OpenAI GPT-4o-mini
* python-dotenv

## How It Works

The application uses a LangGraph `StateGraph` containing two nodes:

### 1. Generate Poem

The `generatePoem` node:

* Takes the topic provided by the user.
* Sends the topic to the OpenAI model.
* Generates a 10-line poem.
* Stores the poem in the graph state.

### 2. Generate Summary

The `generateSummary` node:

* Takes the generated poem from the state.
* Sends the poem to the OpenAI model.
* Generates a summary of the poem.
* Stores the summary in the graph state.

## Graph Structure

```text
START
  ↓
generatePoem
  ↓
generateSummary
  ↓
END
```

## State Management

The workflow uses `TypedDict` to define the state:

```python
class PoemState(TypedDict):
    topic: str
    poem: str
    summary: str
```

The state is updated as the workflow progresses:

```text
Initial State
    ↓
{ topic }
    ↓
generatePoem
    ↓
{ topic, poem }
    ↓
generateSummary
    ↓
{ topic, poem, summary }
```

## Limitations and Possible Improvements

### 1. Fixed Topic

**Limitation:**
The topic is currently hard-coded as `"INDIA"` in the Python code.

**Possible improvement:**
Take the topic dynamically from the user using `input()` or through a web/API interface.

```python
topic = input("Enter a topic: ")
result = poemAgent.invoke({"topic": topic})
```

### 2. Fixed Poem Length

**Limitation:**
The prompt always requests a 10-line poem.

**Possible improvement:**
Allow the user to specify the required number of lines.

```text
User → Topic + Number of Lines
             ↓
        Generate Poem
```

### 3. No Error Handling

**Limitation:**
The current implementation does not explicitly handle errors such as API failures, invalid responses, or network problems.

**Possible improvement:**
Add exception handling and appropriate error messages so that the application can handle failures gracefully.

### 4. Multiple LLM Calls Increase Cost and Latency

**Limitation:**
The workflow makes one LLM call to generate the poem and another LLM call to summarize it. Therefore, both API usage and response time can increase.

**Possible improvement:**
Use an appropriate model, optimize prompts, or combine operations when the application requirements allow it.

### 5. No User Interface

**Limitation:**
The current application runs from a Python script and does not provide a graphical or web-based interface.

**Possible improvement:**
Create a user interface using technologies such as Streamlit, Flask, or FastAPI.

### 6. Limited Workflow

**Limitation:**
The current graph contains only two sequential nodes:

```text
generatePoem → generateSummary
```

There is no conditional routing, validation node, retry mechanism, or human approval step.

**Possible improvement:**
Expand the LangGraph workflow with additional nodes and conditional edges.

For example:

```text
START
  ↓
Generate Poem
  ↓
Validate Poem
  ↓
Is Output Valid?
  ├── No → Regenerate Poem
  │
  └── Yes
       ↓
 Generate Summary
       ↓
      END
```
